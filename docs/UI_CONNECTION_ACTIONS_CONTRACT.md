# P16 断开连接的前端操作契约

范围：已有 `connections()`、`checkConnection(platform)`、`disconnect(platform): Promise<void>` 的前端接入。真实平台连接服务仍待接通；本契约不新增后台操作查询或账号权限。

## 对象与派发

确认显示原平台与原账号。提交前再次读取服务端会话和该平台连接，要求同一已认证用户、平台相同、账号 ID 相同且仍为 `CONNECTED`。账号变更、身份失效、响应错配或读取失败均不派发断开。`accountName` 只作展示，不作身份依据。

派发前把最小记录持久写入用户隔离的 `connection-disconnects` ledger：键为 `[platform, accountId, localRequestId]`，值为 `PENDING` 或 `ACKNOWLEDGED`。不存账号名称、token、Cookie、客户正文或凭据。`localRequestId` 仅为本机操作标识，**没有传给现有服务，不是服务端幂等 ID**。存储不可读/不可写或同平台已有未决记录时，禁止再次断开；重新打开平台登录窗口也检查这份记录。清理本机草稿不删除未决记录。

## 等待、取消和核对

- 身份/连接预检、断开回执等待及状态核对分别有 30 秒上限。关闭弹窗或取消等待立即释放界面；预检阶段取消不派发，已派发后取消不声称撤销服务端操作。
- `disconnect` 的原 Promise 以约定的 `undefined` 成功结束才写 `ACKNOWLEDGED`。迟到回执仅可更新原用户、原平台、原账号的原记录，不改变新页面、不跳转、不弹成功提示。断开失败/超时/响应格式不明保留未知记录。
- 核对只调用现有会话与 `checkConnection(platform)`。`CONNECTED`、`EXPIRED`、`LIMITED`、其他账号或错误平台都不能当作原请求失败或已完成；不自动重发。
- **收到原请求 ACK，且随后读取到原平台 `DISCONNECTED`，账号字段为空或仍匹配原账号，才解除记录并报告已核对断开。** 单独读取到 `DISCONNECTED` 只能说明当前状态，不能伪造原请求 ACK。界面明确保留原结果未知，并阻止该平台再次断开/重新连接。
- 退出页面、切换用户或重新启动后可从列表的“核对断开结果”进入同一记录。新用户看不到旧用户记录；旧用户的原 Promise 后续成功只更新其原 ledger。

## 现有接口的实际限制

`disconnect(platform)` 没有 `expectedAccountId`、连接版本或服务端 requestId，因此前端预检不能替代服务端原子账号校验，跨设备和跨进程也不能靠本机记录保证互斥。服务接入仍必须确保断开只作用当前用户获授权的正确账号，并提供其实际回执语义。

若客户端重启前未收到原 Promise 的 ACK，仅靠当前连接状态无法证明历史请求终态。此时继续保留未知记录并提示核对，不添加“强制清除”来绕过；接入方需提供实际支持路径，后续若扩展可核验的服务端操作契约，再实现安全恢复。此边界不是已完成后台能力。

验证见 `desktop/tests/ui/connection-disconnect.test.tsx`：挂起、取消、迟到、账号/用户错配、重进、清草稿、存储失败、连接状态不等于原操作终态。均使用隔离 TEST 适配，不代表平台实测或 Windows 验收。
