# P14/P15 回复与跟进前端契约

本轮按已批准 R3 P14/P15 及状态矩阵补齐前端。生产 `followups()` / `addFollowup()` 人工登记 facade 继续使用；新增 `YikeService.followup?` 为可选结构化服务，生产尚未接入。类型、控件、隔离测试不能证明真实渠道回复、提醒或客户管理后台已上线。

## 列表、来源与页面入口

P14 保持跟进列表与关联回复两栏。负责人由结构化服务返回的成员清单提供；日期筛选联系时间，未提供联系时间的旧记录按登记日期筛选。按最近联系/登记时间倒序，全部包含历史更正与撤销；待跟进为有下次计划、仍有效且未登记未成交/已成交的事实；回复记录包括人工登记已回复，或服务端明确返回通道回复数量的记录。到期标识是对已保存计划时间的本机比较，不表示已发送通知。

结构化服务的列表是完整记录与成员快照，不接受重复记录 ID；字段、版本或时间无效进入可刷新的错误态。旧 facade 不提供负责人、联系时间、结构化计划或通道数量，界面明确显示“未提供”，不从备注猜字段。旧数据在待跟进标签下有明确的人工登记范围说明，不冒称到期提醒。

工作台可通过 `#/followups?opportunity=<id>&tab=todo|replies` 定位目标商机最新登记。首次载入时显示该目标，即使最新登记不属于当前队列的普通筛选；提示“已定位目标商机的最新登记”。目标不存在或不可访问时明确报告，不选其他客户。之后本地选行、改标签或筛选优先，刷新不会反复拉回原目标。`add=1&opportunity=<id>` 只预选新登记的商机，不对尚无历史记录报定位错误。

## 服务对象与回复关联

定义见 [followup.ts 类型](../desktop/src/renderer/domain/followup.ts) 和 [FollowupService](../desktop/src/renderer/services/followup.ts)：

- `list()` 返回人工 `records` 和 `members`。每条记录具有记录 ID、商机 ID、画像版本、正整数 revision、实际联系时间、事实类型、备注、下一步、下次跟进、负责人及 `ACTIVE / CORRECTED / VOID` 状态。通道回复数量可选，必须来自服务端。
- `replies(opportunityId)` 只返回该商机的通道回复；不传 ID 时只返回尚未匹配商机的回复。每条回复有自身 ID/revision、商机/画像版本/发送请求关联、内容、时间、平台、已读状态和 sample 标记。重复 ID 或错误商机关联拒绝展示。
- `mutate({binding,values?,reason?})` 执行新增、纠正、撤销或标为已读；`operation(binding)` 只读核对原请求，不创建新动作。

通道回复与人工登记在两个标签中独立展示。未匹配回复保留原因；没有可核验的商机与发送记录时不能标已读，也不伪造关联。样例只读，不写客户事实、不修改已读状态。来源真实性、所属租户、回复事件去重和发送关联由服务端验证，页面不能将人工填写变成渠道回执。

## 新登记、实际时间与未保存保护

P15 保留关联商机、人工类型、事实类型、联系时间、备注、下一步、下次跟进和负责人。联系时间选填，填写时不得在未来；备注必填，备注与下一步分别最多 500 字。下次跟进允许记录历史计划，从而能展示到期状态；当前 date 控件按本机时区的该日 09:00 转成 ISO 时间，日期/时间语义必须由后续真实服务保持一致。负责人只能从真实服务返回的成员中选择。

现有人工 facade 只有商机、状态、备注三字段。因此这些新增字段仍可编辑，在没有结构化服务时，联系时间、下一步、下次跟进会以明确的“人工登记补充；未设置提醒”段落随备注保存；不丢掉用户输入，也不假称已创建结构化计划。负责人为当前登记成员，不提供未接通的成员分配。旧接口实际返回成功后才关闭抽屉。

保存前重新读取客户商机，拒绝样例、消失商机及画像版本/更新时间变化。可选结构化服务要求真实非空画像版本；旧 facade 缺版本时本机锁使用 `legacy-unversioned` 标记，不能把它当服务器版本。保存失败、未知或关闭后草稿保留在当前用户的本机会话；取消会要求确认保留后关闭。成功保存先移除未保存保护再导航，不重复弹离开确认。用户/服务变更或卸载后的迟到成功可结算原用户操作锁，但不能清新用户草稿、跳页或发成功提示。

## 纠正、撤销与已读

只对有效、非样例人工记录提供纠正/撤销。纠正必须填写原因，提交前重新读取原记录 revision 与商机版本；成功产生新的有效记录并通过 `correctsId` 指向原记录，原记录与原始内容仍保留。撤销需要原因与单独确认，回执必须指向原记录、增加 revision 并标为 VOID。前端没有删除历史审计的路径。

已读操作同样核对原回复 revision、商机画像版本及发送关联。成功回执必须为原回复、更新 revision 并明确 read=true。保存/已读/撤销后重新加载列表或回复，以服务返回状态为准。

## 幂等、未知结果与本机边界

每个结构化变更携带六项绑定：

```text
[opportunityId, profileVersionId, action, targetId, targetRevision, requestId]
```

action 限 `create / correct / void / mark-read / legacy-create`。新建 targetId 为空、targetRevision=0；修改必须指定原对象与 revision。随机 requestId 在调用前与绑定一起写入用户隔离 `followup-operations` ledger，值仅 PENDING；不保存备注、回复全文、凭据。单项和总 key 长度受共享校验限制；存储失败、损坏或联合 ID 过长均不得派发。存在未决操作时不能再次保存；清草稿、关闭或同用户重登不移除它。

结构化服务须持久幂等、重验商机/版本/成员/记录归属，并以事务或可审计补偿保存业务记录及操作回执。前端只接受与原六项绑定完全相同的回执；直接保存成功时还比对返回记录与提交字段快照。

| 回执 | 页面处理 |
| --- | --- |
| SUCCEEDED 且 confirmed=true，附身份与状态匹配的记录/回复 | 结算原请求；更新后的真实记录再由列表刷新读取 |
| FAILED 且 confirmed=true | 结算原请求、保留草稿，允许核对后重试；服务端只能用来表达确定未完成的终态 |
| PENDING / UNKNOWN、HTTP 错误、超时、缺少/错配回执 | 保留原请求，不盲重试 |

界面等待上限 30 秒，超时不是取消。`operation()` 必须查询原 requestId；不存在回执不是确定失败。本机记录不能替代服务端幂等，也不提供多设备并发执行保证。

旧人工 facade 没有原 requestId 查询能力：其成功返回可结束本机保存；不确定失败保留锁与草稿，提示核对已有登记并由服务管理员确认，不能猜测内容相似就当作原请求成功，也不能借清草稿重发。真正完整的未知恢复需要结构化后台接入，本轮明确保留这个接入缺口。

## 验证与仍缺能力

新增隔离测试覆盖列表/负责人/日期、回复关联/未读、样例、纠正与撤销、原操作锁及无效键、版本变化、30 秒超时、换用户迟到、工作台入口，以及真实 AppProvider 的保存/取消/hashchange。原人工 facade 测试继续保留。测试位于 `desktop/tests/ui/followup-*.test.tsx`，夹具不注入生产服务。

未完成的真实接入包括：结构化记录/成员、不可变纠正链、通道回复回流与去重、已读同步、服务端幂等/原请求核对、提醒调度。这里只提供已批准页面范围的可用条件前端与契约，不宣称这些生产能力已通。
