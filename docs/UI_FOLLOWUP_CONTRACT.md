# P14/P15 回复与跟进前端契约

本轮按已批准 R3 P14/P15 及状态矩阵补齐前端。生产 `followups()` / `addFollowup()` 人工登记 facade 继续使用；新增 `YikeService.followup?` 为可选结构化服务，生产尚未接入。类型、控件、隔离测试不能证明真实渠道回复、提醒或客户管理后台已上线。

## 列表、来源与页面入口

P14 保持跟进列表与关联回复两栏。负责人由结构化服务返回的成员清单提供；日期筛选联系时间，未提供联系时间的旧记录按登记日期筛选。按最近联系/登记时间倒序，全部包含历史更正与撤销；待跟进为有下次计划、仍有效且未登记未成交/已成交的事实；回复记录包括人工登记已回复，或服务端明确返回通道回复数量的记录。到期标识是对已保存计划时间的本机比较，不表示已发送通知。

结构化服务的列表是完整记录与成员快照，不接受重复记录 ID；字段、版本或时间无效进入可刷新的错误态。旧 facade 不提供负责人、联系时间、结构化计划或通道数量，界面明确显示“未提供”，不从备注猜字段。旧数据在待跟进标签下有明确的人工登记范围说明，不冒称到期提醒。

工作台可通过 `#/followups?opportunity=<id>&tab=todo|replies` 定位目标。左侧若已有该商机的人工记录，首次载入定位最新登记，即使它不属于当前队列的普通筛选；没有人工记录不再被当成商机不存在。右侧关联回复以目标商机 ID 独立读取，不依赖左侧记录、回复数量或状态筛选才能进入。

右侧“查看商机回复”选择器提供当前授权商机和明确的“未匹配回复”选项。目标来自路由、明确选行或选择器；之后用户本地选择优先，刷新、日期/负责人筛选或左侧标签切换不暗中改成其他商机或未匹配回复。当前目标即使不在 `opportunities()` 列表内，仍可通过精确 `opportunity(id)` 验证并保留其选择，不能用列表第一项代替。`add=1&opportunity=<id>` 预选新登记商机，不要求已有历史记录。

## 服务对象与回复关联

定义见 [followup.ts 类型](../desktop/src/renderer/domain/followup.ts) 和 [FollowupService](../desktop/src/renderer/services/followup.ts)：

- `list()` 返回人工 `records` 和 `members`。每条记录具有记录 ID、商机 ID、画像版本、正整数 revision、实际联系时间、事实类型、备注、下一步、下次跟进、负责人及 `ACTIVE / CORRECTED / VOID` 状态。通道回复数量可选，必须来自服务端。
- `replies(opportunityId)` 只返回该商机的通道回复；不传 ID 时只返回尚未匹配商机的回复。每条回复有自身 ID/revision、商机/画像版本/发送请求关联、内容、时间、平台、已读状态和 sample 标记。重复 ID 或错误商机关联拒绝展示。
- `mutate({binding,values?,reason?})` 执行新增、纠正、撤销或标为已读；`operation(binding)` 只读核对原请求，不创建新动作。

指定目标时，`useRelatedReplies` 先有界读取 `YikeService.opportunity(id)`：返回对象必须与请求 ID 完全相同且不是公开样例，再读取该 ID 的 `replies(id)`。详情不存在、无权限、失败、超时、错 ID 或样例均显示可恢复状态，不改查未匹配回复，也不打开别的客户；目标详情读取独立于人工 `list()` 和商机列表是否为空/读取失败。只有用户明确无目标时，才调用不带 ID 的 `replies()` 读取 `opportunityId=null` 的未匹配集合。列表仅供选择，真实归属与权限仍由服务端逐次校验，不能靠前端 ID 检查代替。

通道回复与人工登记在两个标签中独立展示并保留各自加载、错误和重试：人工列表失败不隐藏已验证目标的通道回复；回复读取失败不把人工登记改为空，也不阻止依赖已具备时添加人工事实。人工记录读取失败时显示错误，不能显示“暂无关联登记”。目标详情尚未通过验证时两类内容都不借旧目标展示。未匹配回复保留原因；没有可核验的商机与发送记录时不能标已读，也不伪造关联。样例只读，不写客户事实、不修改已读状态。来源真实性、所属租户、回复事件去重和发送关联由服务端验证，页面不能将人工填写变成渠道回执。

## 新登记、实际时间与未保存保护

P15 保留关联商机、人工类型、事实类型、联系时间、备注、下一步、下次跟进和负责人。联系时间选填，填写时不得在未来；备注必填，备注与下一步分别最多 500 字。下次跟进允许记录历史计划，从而能展示到期状态；当前 date 控件按本机时区的该日 09:00 转成 ISO 时间，日期/时间语义必须由后续真实服务保持一致。负责人只能从真实服务返回的成员中选择。

现有人工 facade 只有商机、状态、备注三字段。因此这些新增字段仍可编辑，在没有结构化服务时，联系时间、下一步、下次跟进会以明确的“人工登记补充；未设置提醒”段落随备注保存；不丢掉用户输入，也不假称已创建结构化计划。负责人为当前登记成员，不提供未接通的成员分配。旧接口实际返回成功后才关闭抽屉。

保存前重新读取客户商机，拒绝样例、消失商机及画像版本/更新时间变化。可选结构化服务要求真实非空画像版本；旧 facade 缺版本时本机锁使用 `legacy-unversioned` 标记，不能把它当服务器版本。保存失败、未知或关闭后草稿保留在当前用户及客户空间版本的本机会话；取消会要求确认保留后关闭。成功保存先移除未保存保护再导航，不重复弹离开确认。

从已验证的回复目标点击“添加跟进”，即使该商机不在列表或尚无人工记录，也能预选其精确详情；结构化成员等保存依赖仍必须可用。保存或明确“保留并关闭”后移除 `add=1`，保留原商机及当前 `todo / replies / all` 标签；重新打开同目标时保留未保存草稿。关闭确认中取消则留在原抽屉，输入不丢失。查看回复或标为已读不自动制造人工跟进记录，只有用户显式保存事实才新增登记。

页面、列表、回复、编辑草稿和预检按用户、认证状态、服务实例及可信 `accountScope.id/version` 隔离。同账号切空间或空间版本也立即隔离旧内容；旧预检不得继续派发变更。用户、空间、服务变更或卸载后的迟到成功不能结算原操作锁、清新草稿、跳页或发成功提示；返回原客户空间的精确版本后，用户通过原请求核对。这取代较早仅按 userId 隔离、允许离页晚到回执清锁的做法。

## 纠正、撤销与已读

只对有效、非样例人工记录提供纠正/撤销。纠正必须填写原因，提交前重新读取原记录 revision 与商机版本；成功产生新的有效记录并通过 `correctsId` 指向原记录，原记录与原始内容仍保留。撤销需要原因与单独确认，回执必须指向原记录、增加 revision 并标为 VOID。前端没有删除历史审计的路径。

已读操作同样核对原回复 revision、商机画像版本及发送关联。成功回执必须为原回复、更新 revision 并明确 read=true。保存/已读/撤销后重新加载列表或回复，以服务返回状态为准。

## 幂等、未知结果与本机边界

每个结构化变更携带六项绑定：

```text
[opportunityId, profileVersionId, action, targetId, targetRevision, requestId]
```

action 限 `create / correct / void / mark-read / legacy-create`。新建 targetId 为空、targetRevision=0；修改必须指定原对象与 revision。随机 requestId 在调用前与绑定一起写入 `yike.ui.followup-operation.v2` 的 owner envelope；owner 包含 userId 及 accountScope 的 ID/版本，没有可信 scope 的旧 facade 使用显式 null 范围。键与值的 owner、原六元绑定必须一致。来自 P15 的请求还保存本机会话草稿键和提交内容的 SHA-256；这些仅为前端恢复元数据，不加入服务请求，也不保存备注、回复全文或凭据。各 ID、revision 与请求结构严格校验，写入后回读；存储失败、损坏或身份不匹配时不得派发。存在未决操作时不能再次保存；清草稿、关闭或重登不移除它。

旧用户级 v1 操作不自动归入当前空间：保留并展示原 requestId，禁止当前空间查询或覆盖。旧 session-only 操作在尚未打开 P14 时也受全局清草稿保护；首次读取后先可靠保留到原用户的持久旧 ledger，同样保持未绑定。当前同空间旧版本、scope 缺失的历史操作显式阻断；其它已知客户空间的操作保留，但不在本空间查询、结算或展示为本空间任务。终态只能删除当前精确 owner 的原请求，并回读确认删除成功。

结构化服务须持久幂等、重验商机/版本/成员/记录归属，并以事务或可审计补偿保存业务记录及操作回执。前端只接受与原六项绑定完全相同的回执；直接保存成功时还比对返回记录与提交字段快照。

| 回执 | 页面处理 |
| --- | --- |
| SUCCEEDED 且 confirmed=true，附身份与状态匹配的记录/回复 | 结算原请求；对绑定的同一提交稿登记当前会话的 hash 确认，更新后的真实记录再由列表刷新读取 |
| FAILED 且 confirmed=true | 结算原请求、保留草稿，允许核对后重试；服务端只能用来表达确定未完成的终态 |
| PENDING / UNKNOWN、HTTP 错误、超时、缺少/错配回执 | 保留原请求，不盲重试 |

原请求核对为确定成功后，P15 只有在草稿键、客户空间版本及完整表单 SHA-256 都与原提交一致时才清理旧稿；重新打开与快速点击保存两条路径都核对，不能以新 requestId 重复登记已确认的同一稿件。用户在未知期间修改的稿件、FAILED 原稿仍保留，不清其它请求或空间的草稿。成功确认标记与草稿同为当前本机会话数据，但标记必须先写入 sessionStorage 并回读一致，才能发布到内存及删除持久原请求锁。写失败、静默不写或读取失败均保留原锁与稿件。清理原稿后还要确认存储中原稿已不存在，才消费其 hash 标记；原稿删除失败时标记继续保留，刷新后不会复活可再次提交的旧稿。旧操作缺少草稿快照时不推测对应正文、不自动清理。

界面等待上限 30 秒，超时不是取消。`operation()` 必须查询原 requestId；不存在回执不是确定失败。本机记录不能替代服务端幂等，也不提供多设备并发执行保证。

旧人工 facade 没有原 requestId 查询能力：其确定成功返回也必须共用可靠的提交稿 hash 确认，再结束本机保存，不能绕过结构化分支的防重复收尾；若接口已返回成功而本机 ACK 或清锁失败，页面明确区分已收到接口成功与本机确认失败，保留原请求保护，需核对已有登记并由服务管理员确认，不创建虚构 operation 回执；不确定失败保留锁与草稿，提示核对已有登记并由服务管理员确认，不能猜测内容相似就当作原请求成功，也不能借清草稿重发。真正完整的未知恢复需要结构化后台接入，本轮明确保留这个接入缺口。

## 验证与仍缺能力

新增隔离测试覆盖列表/负责人/日期、回复关联/未读、样例、纠正与撤销、原操作锁及无效键、版本变化、30 秒超时、换用户迟到、同用户切空间/空间版本、旧 v1/旧空间版本保留、原空间精确核对、成功恢复稿件防重复及修改稿/FAILED 稿保留、工作台入口，以及真实 AppProvider 的保存/取消/hashchange。`followup-reply-entry.test.tsx` 与 `followup-reply-flow.test.tsx` 另覆盖无人工记录及列表外精确目标、错误目标不回落、选择器、通道/人工读取独立错误、标已读不造记录、添加/保存/取消后目标与标签保留。原人工 facade 测试继续保留。测试位于 `desktop/tests/ui/followup-*.test.tsx`，夹具不注入生产服务；测试通过不替代 CUA 可见验收或真实回复回流。

未完成的真实接入包括：结构化记录/成员、不可变纠正链、通道回复回流与去重、已读同步、服务端幂等/原请求核对、提醒调度。这里只提供已批准页面范围的可用条件前端与契约，不宣称这些生产能力已通。
