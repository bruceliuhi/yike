日期：2026-09-09。
依据：用户明确要求补齐缺失的必要功能，不能以当前代码能力压缩产品吸引力和付费价值。
状态：当前正式产品目标与交付标准，已纳入本分支实施范围；新增功能尚未完成。本文件定义任务及验收，进度唯一来源为 [V0.2 实施任务书](V02_IMPLEMENTATION_TASKBOOK.md)。本文件不是上线或商业效果证明。
目标代码基线：`yike-ai2026 / codex/customer-pilot / f82a9ae`，与演示来源分支的差异见 [迁入说明](V02_DESIGN_HANDOFF.md)。现有 CP-01～CP-05 是复用基础，CP-06 是部署子门禁；本计划定义当前完整获客版，功能与部署完成标准分别记录。
设计状态：沿用蓝白科技风、Y Logo 和分组左侧导航；用户仍要求设计图选定后再进行页面实现。后台协议、执行器和存储设计可与视觉工作并行。

## 1. 产品承诺与首发边界

意客AI帮助服务商持续发现值得联系的潜在客户，说明判断依据，完成联系并跟进结果。

首个完整付费版必须包含：软件登录与平台连接、任务配置、真实线索采集、增量监控、AI意向判断与证据、商机复核、真实触达执行、回复及跟进、可安装交付与支持。

现有实现是复用基础，不是产品功能上限。“人工导入研究包＋复制草稿”属于中间开发里程碑，不能作为这一完整获客版的最终交付或被改名替代缺失能力。

用户最新明确要求首发监控多个平台，并采用当前分支商机研究 Skill 的方式。因此首个完整付费版改为多平台采集与监控；具体建议清单为小红书、抖音、B站、知乎与公开网站/社区，逐平台完成真实运行验收。通用研究 Skill、平台 Skill、实际连接器和调度系统的分工见 [多平台 Skill 监控方案](V02_MULTIPLATFORM_SKILL_PLAN.md)。一套行业模板和已接通的触达渠道可先做深，不能再用单平台替代多平台交付。首次行业验证可从展台设计搭建开始，但现有公告样例不证明任何社交平台对该行业已有效。

用户已明确取得 MediaCrawler 商业授权，直接采用该代码复用路线；对外统一意客AI品牌，不展示内部引擎名称。技术记录保留依赖版本与溯源。

## 2. 客户付费动机与验收功能

| 功能 | 首发必须包含 | 预期价值与证据 |
|---|---|---|
| 账号与授权 | 产品激活/登录/退出；客户空间；平台扫码连接、账号身份与失效状态、重新连接和断开；各账号会话隔离 | 客户可自行配置使用；用真实登录/失效/恢复验证。连接方式按实际实现命名，不假称官方 OAuth |
| 业务画像与资料 | 服务、地区、客群、排除项；真实产品/案例资料；AI提取草稿后由用户确认；资料版本及引用范围 | 让检索和联系内容贴合客户业务；不凭空编造服务能力、案例和业绩 |
| 获客任务 | 关键词/排除词、视频或作者链接、任务范围、运行周期；保存模板；预览配置、启动/暂停/恢复 | 将业务目标变成可重复运行的任务，减少配置成本 |
| 线索采集 | 首发多个平台实际关键词搜索、支持范围内的内容/评论采集；来源ID、URL、原文、时间、分页与去重；逐平台进度及失败原因 | 减少人工搜索与翻评论；一项业务任务覆盖多个来源，零结果如实显示 |
| 持续监控 | 一任务选多个平台，分别定时运行、维护游标和内容版本；上次/下次执行、暂停/恢复、独立重试、部分成功和新增提醒 | 多个平台持续提供新发现；单平台受阻不拖停其他平台；重复不冒充新增，本地离线如实显示 |
| AI意向判断 | 需求、区域、采购阶段、时间与预算的证据提取；需求方/同行/广告/无关判断；匹配理由、反证、未知项；人工纠错 | 让销售快速判断是否值得联系；匹配程度不冒充成交概率 |
| 商机工作台与库 | 待复核、待联系、待回复、待跟进视图；原文与独立判断；筛选、批量复核、重复关联、导出；所有统计来自真实记录 | 帮客户决定今天先处理谁；原始候选与已确认商机分开 |
| 触达中心 | 结合原文与真实业务资料生成并保存独立草稿；确认对象、内容、渠道；通过真实适配器执行；发送状态、回执、失败原因、暂停、去重 | 从发现需求走到实际联系。复制功能可保留，但不等于发送；不确定发送结果不得盲目重试 |
| 回复与客户跟进 | 对已接通渠道接收并关联回复；未读/待跟进提醒、负责人、标签、备注、下一步时间；联系与回复时间线 | 减少遗漏。通道事件和人工登记分别标识，不把发送成功当作客户回复 |
| 商业交付 | Windows 安装/卸载、激活与试用有效期、更新与版本回退、凭据私有存储、备份恢复、数据导出、支持入口与可脱敏诊断 | 客户能安装、持续使用和处理故障。发行包、渠道稳定性与售后共同构成可交付产品 |

所有价值是待验证假设，不是既有业绩。第一版可以不支持高级团队权限、充值商城、代理商系统、完整 CRM 合同财务，但基础使用授权、客户空间隔离和数据恢复必须可用。

## 3. 最有说服力的三个演示时刻

1. 客户填写自己卖什么、服务哪里、想找什么人；确认任务后，系统实际搜索并带回可打开的需求原文。客户自己判断“这条是否值得联系”。没有符合结果时，应调整任务或说明没有结果。
2. 查看同一任务的两个真实运行批次：第二次只推送新增或实质变化；打开一条线索看到命中证据、排除原因和建议动作。展示系统为什么值得持续使用。
3. 审核针对某条需求的草稿，向明确授权的验收对象实际发送，显示真实状态；收到测试回复后回到同一商机的跟进时间线。测试账号明确标识，不能作为客户转化业绩。

静态公开询价样例继续用于讲清证据结构，不再承担整套获客软件的主要销售演示。下一轮视觉重点覆盖“获客任务创建/执行”“新增线索与意向复核”“触达与回复跟进”三个关键场景；保留已经确定的蓝白视觉体系。

## 4. 导航与页面组织

保留目前八个一级入口：商机工作台、业务画像、线索采集、监控任务、商机库、触达中心、跟进记录、账号与授权。

- 获客任务创建与模板作为线索采集的主入口，单次运行结果可转为持续监控；任务配置复用业务画像。
- 视频、作者、评论属于来源类型与筛选维度，不各建一套互不贯通的客户库。
- 资料与案例属于业务画像内的业务资料标签页；话术版本属于触达中心。
- 工作台突出真实待处理队列和“新建获客任务”入口；运行数量、线索数量和联系结果仅来自数据库。
- 每个页面围绕一个主要动作，详情、发送确认和任务配置渐进展开；功能丰富通过完整流程表达。

| V02-10 集成、独立审核与客户试用 | 锁定实现提交；架构/代码/质量独立复核；真实账号闭环、恢复演练及试用交付 | 02–09 | 全流程证据绑定发布版本；客户自行完成任务；问题可定位；实际服务端交付必须完成 CP-06，适用于公网或私有客户环境 |

关键适配风险应提前验证：现有平台 browser profile 按平台固定，不能直接用于多客户；旧执行器存在 Unix 进程管理，Windows 支持不能仅放在最后套壳。真实发送通道与 Windows 执行可行性和首轮采集并行验证。

采集与触达之间必须保存来源用户标识、通道收件人标识、映射依据、可联系条件及不可联系原因；不能根据相似昵称猜测跨平台身份。整链验收采用明确授权且可从采集来源回查的对象，证明“采到的人”确实能在该通道联系并关联回复。

状态模型、字段和接口只放入明确模块：平台会话 / 采集适配 / 任务执行 / 意向处理 / 触达适配 / 跟进事件。保留现有 Web 路由薄层，不把全部逻辑追加到一个大文件。

## 6. 里程碑与发布规则

- M1：多平台连接＋逐平台真实首次采集＋原始结果，可内部演示；阶段性单平台贯通仅算子任务完成。
- M2：多平台持续监控＋Skill意向筛选＋用户复核＋统一商机工作台，可邀请客户检验线索价值。
- M3：真实触达＋回复回流＋跟进＋Windows交付＋独立验收；实际服务端交付通过 CP-06（含私有客户环境），形成首个完整付费版。

可按里程碑预览和修正，不将 M1/M2 宣布为用户所要求的完整获客版。任何首发必需能力遇到问题，都保留在交付清单并安排解决任务，不能默默删除后称已完成。若具体平台确实不支持某路径，记录事实与可行替代，经产品范围决策处理，而不是无限期“后续再说”。

研发可分批交付，但第一付费版的目标清单保持完整。源代码授权已经由用户确认，后续不重复索取。

## 7. 客户验证与收费方式

买单人假设：拥有真实服务交付能力、目前靠人工找需求或获客成本较高的小企业老板/销售负责人。现有展台行业资料用于启动实验，不能代替实际客户验证。

初期可采用“软件试用/使用许可＋任务配置与上线辅导＋明确范围的支持”交付，先人工开通和对公收款，不因缺充值商城延误验证。正式报价先列清来源、账号/设备、运行与模型用量、支持周期和外部成本；试点数据出来前不写保证线索数量或成交的套餐。

建议3家同一行业、7–14天，开始前约定合格线索的业务标准并采集人工工作基线。记录：

- 此前未知、客户认可且能采取下一步行动的去重线索数；
- 人工筛选耗时与软件辅助后耗时；
- 实际联系、有效回复、下一步约谈/报价；区分技术送达与业务有效回复；
- 任务运行稳定性、干预次数、单位有效线索成本；
- 实付、实际使用和续费意向。

付款证明购买意愿，持续使用和续费检验实际价值。若完整流程稳定但客户仍不认可线索，应调整目标客群、来源和识别规则；不能仅用增加菜单解释失败。
