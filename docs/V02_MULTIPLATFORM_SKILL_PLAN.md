状态：V1.0 当前正式多平台技术方案；V1.1 数据驱动扩展仅保留设计。多平台定时执行尚未实现，不以本文件或平台菜单作为已支持证明。MP 子项映射到 [V02 实施任务书](V02_IMPLEMENTATION_TASKBOOK.md) 的主任务，进度只在该台账维护；版本增量见 [V1 版本映射](V1_VERSION_MAPPING.md)。

### 2026-09-22 增量游标实现状态

B站与小红书现在共用同一套服务端 claim/commit 原子游标合同，但使用各自的适配器版本：`bili-search-items-v1` 与 `xhs-search-items-v1`。小红书游标固定保存 `search_id`、页码、已消费笔记 ID 和刷新阶段；Windows host、Python MediaCrawler 适配器、桌面端 schema、候选上传校验和回放测试已贯通。该变更只证明代码和合成回放合同通过，**尚未证明 Windows 实机登录、真实小红书三轮连续采集、平台响应稳定性或客户价值**；抖音、B站、知乎仍不能因平台菜单存在而自动获得同等增量能力。

### 2026-09-22 平台增量边界复核

- **抖音暂不接入持久增量游标**：固定依赖的搜索接口以 `offset + search_id` 请求，返回只有结果列表和动态 `extra.logid`，没有可验证的 `has_more`/总量/结束标志；当前采集器的请求数量与 offset 步长还存在重叠。没有真实响应样本证明排序、`logid` 和重启后的分页位置稳定前，不能把平台枚举放宽后宣传为“持续增量监控”。抖音继续提供受账号保护的普通轮次采集。
- **知乎具备下一条可实施路径，但尚未接入**：受控补丁已经严格校验 `paging.is_end` 与 `paging.next`，但现有 `get_note_by_keyword` 丢弃了下一页游标，核心流程固定从第 1 页读取。要接入，必须新增知乎专用 adapter version，保存并校验受限的 `paging.next` URL、页内内容 ID 和刷新阶段，同时更新 MediaCrawler patch、锁文件哈希、Windows host、桌面 schema、服务端 claim/commit 和真实 PostgreSQL/Windows 回放测试。

这两个结论是能力门禁，不是产品降级：菜单可以展示平台连接状态，但只有完成上述逐平台游标契约和真实运行验收后，才允许在持续监控能力中标记“可用”。

## 产品体验

客户输入企业介绍、公开网站或支持格式的业务资料，确认多产品/服务、客群与销售方式；系统建议适用来源、需求表达、关键词/排除项和判断规则。客户可编辑并确认监控对象、范围、频率及预算后创建任务。系统按平台独立运行，统一输出新增需求、实质变化、判断证据和下一步建议。客户可以按平台看来源，也可以在同一商机库处理全部结果；输入不支持、解析失败、资料不足时明确提示并允许补录。

Skill 和底层采集引擎属于内部实现。对外仍展示意客AI、监控任务、平台连接和商机证据，不要求客户理解 Skill 或选择技术引擎。

## 多平台范围

V1.0 的“多找类似”只能在已验收的来源、已确认的任务范围和预算内扩搜；未接通来源不算已支持。V1.1 才根据本客户的真实有效率扩展作者/话题和优化预算，且保留探索份额。V1.0 只记录来源、查询、画像/规则版本、成本和反馈溯源字段，不提前造自动学习系统。

首个完整付费版要求真实多平台监控。建议首发具体清单为小红书、抖音、B站、知乎四个内容平台，加公开网站/社区来源；此为待实施的建议清单，不是现有可用能力列表。微博、贴吧、快手以及公众号/视频号进入相同的平台注册与平台 Skill 规划，按各自入口完成适配。

| 平台组 | Skill 方法 | 连接路径与需完成工作 |
|---|---|---|
| 小红书、抖音、B站、知乎 | 业务表达扩展；搜索、原帖/评论核验；买方身份与需求状态判断 | 复用用户已获商业授权的采集依赖；逐平台规范字段、会话、游标、错误、受限恢复，接入客户执行器 |
| 公开网站/社区 | 按站点和版块检索；打开原文；跟踪话题/页面变化；排除过期和供应商内容 | 通用网页/检索连接器加站点读取规则；如有可用官方API、RSS则优先使用。搜索摘要只作发现入口 |
| 微博、贴吧、快手 | 复用通用研究方法，追加平台内容结构与买方信号规则 | 底层依赖有相应平台代码；仍须独立接入并运行验收，不能仅添加名称 |
| 公众号、视频号 | 公众号文章与视频号内容分别定义检索/读取/评论/监控方法 | 单独连接器；本次所查依赖的支持表未包含微信这两个入口。列为明确开发项，不假设能直接套现有适配 |

底层能力参考：[固定依赖版本 README 支持表](https://github.com/NanmiCoder/MediaCrawler/blob/439509782cc2991c8ef7648e178d5847b0545798/README.md)。用户已明确取得商业授权，不重复要求确认；不将商业代码授权等同于平台会话或接口能力。

每个平台分别登记搜索、原文、评论、增量检测、发送、回复六类能力。监控支持与触达支持分别验收：能读取公开原文，不自动证明能读取全部评论或向来源作者发送消息。

跨行业来源评估纳入 V02-02：采购公告、企业公开动态、行业网站按具体站点/接口记录适用业务、能力、成本与首发范围决定，不能仅因存在通用 web 连接器就承诺全网覆盖。读不到的来源和无法确认的主体保留未知；不按相似昵称推断个人真实身份。

任务创建增加基于已确认画像的搜索条件建议：通用规则理解产品/服务、目标客户、销售方式与采购表达，行业策略定义有效信号与反例，平台规则把建议转换为各自支持的查询。建议输出与原始候选/商机分开，必须由用户确认最终配置后执行；重新生成不能覆盖人工编辑，也不能自动增加连接平台、监控频率或费用预算。[搜索条件交互和验收（R3 沿用 R2 行为）](../design/v02-suite-r3/AI_SEARCH_CONDITIONS.md)由 V02-04/V02-05 接入，当前规则包不等于该生成服务已实现。

行业策略是通用研究层中的版本化配置，不为每个行业复制整套执行器。输入包含已确认画像/资料版本、产品与服务组合、客户类型、地域、销售方式及排除条件；输出包含来源建议、需求表达、判断依据、反例、未知项及预算。制造/贸易、专业服务、软件/数字服务、本地生活、零售/品牌作为代表性评测集，未列出的行业可自定义，模板不得成为行业准入条件。策略、画像、平台规则及模型版本随任务和分析结果一起保存；字段/API 仍须由 V02-04/05 定义并联调，本段不表示当前 DTO 已具备这些字段。

## 四层结构

1. **通用商机研究 Skill（含行业/销售方式策略）**：解释已确认业务画像、扩展买方表达、制定查询、提取证据、匹配与排除、给出联系建议。分别判断业务匹配、意向、紧迫性和可行动性；统一事实/推断/未知，保留独立评论和私信草稿。
2. **平台 Skill**：各平台检索词、可读页面、原帖/评论定位、时间解释、字段映射、失败判定和增量策略。引用同一套通用判断规则，不复制整套业务逻辑。
3. **工具连接器**：实际调用浏览器、已授权采集代码、API或网页读取工具；会话与执行由代码管理，返回结构化来源和可重开的证据。
4. **任务与数据系统**：定时启动、并发预算、账号锁、心跳、重试、暂停/恢复、游标、去重、提醒、租户隔离和审计。持续运行不依赖 Agent 自己记住何时醒来。

以下为建议新增模块，不表示目录已经存在：skills/ 保存研究方法与平台规则；pilot/monitoring/ 管理配置和执行；pilot/connectors/ 定义能力协议；桌面执行器持有隔离的本机账号会话，经 HTTPS 候选 API 接入服务端且不持有数据库连接；pilot/evidence/ 管来源与候选；pilot/intelligence/ 执行和校验 Skill 输出；商机与触达沿用独立业务模块。

Skill 包需包含版本与依赖、输入/输出约定、允许调用的工具、必需能力、执行预算、恢复点与代表性反例。无须为每个平台另造一个完整 Agent 系统。

## 一次监控怎么运行

1. 保存监控定义，绑定客户身份、画像与行业策略版本、所选平台和各自连接。
2. 到期后为每个平台创建独立运行项，记录 Skill/连接器版本、查询、窗口、增量游标和预算；平台子任务互不共享会话。
3. 先搜索/读取，写入原始候选与来源观察；有新内容或实质变化才调用意向分析，避免重复消耗模型费用。
4. 校验模型引用的原文、时间和身份；AI 结果进入待复核候选。用户经独立复核接口操作，服务端解析身份与复核时间；设备或模型不能伪造 reviewer 或 APPROVED 直接进入已复核商机。
5. 用户复核后进入统一商机库。跨平台同项目只建立可解释关联；没有依据不能按昵称合并为同一人。
6. 原子保存有效结果和游标，产生一次新增/变化提醒；本轮各平台可分别成功、无新增、需登录、受限或失败，父任务如实汇总为部分完成。

任务配置与单次执行分开，建议增加 monitor_definitions、monitor_platform_bindings、monitor_runs 和 monitor_run_steps。
目标分支现有 pilot_tasks 与 research:画像版本绑定，提供单个任务的领取/完成/失败/查询基础，不能直接充当多平台监控表；客户侧任务列表、周期与平台执行明细需新增。

每次领取任务增加执行代次。候选写入、游标更新和完成状态必须在同一短事务校验当前 owner/代次，拒绝失去租约的旧执行者回写；浏览器、模型和网络调用在事务外执行。当前 complete/fail 的 owner 检查不能替代结果写入校验。

按账号与平台独立退避，允许一个平台失效而其他平台继续执行。无新增与无法读取分开记录；不可见的评论不能算已检查。
运行间隔由来源能力、时效需求与预算决定；定时搜索、定时评论检查、事件订阅分别命名，不把所有模式统一宣称秒级实时。
本地执行器离线时显示离线；需要离线仍执行的客户再选择具备实际工具和连接能力的云端执行器。

## 实施任务与验收

以下 MP 编号是技术子项，不是第二套开发台账；与 V02-01～10 的归属见实施任务书。

- MP-01：将现有通用研究规则整理入库，拆平台规则与共享输出契约，明确实际执行入口；当前已完成规则包迁入，仍需接入 V02-04 运行入口并用已有反例和真实候选验收。
- MP-02：平台能力注册、任务配置/运行分离、逐平台会话与游标、预算和部分成功汇总；B站与小红书的持久游标代码已接入，仍需目标 Windows 环境验证。
- MP-03：首发四个平台和公开网站连接器分别接入；复用旧采集器时解除双平台硬编码与共享平台目录问题。
- MP-04：Skill 执行结果进入原始候选/分析层；复用现有证据、复核、版本和商机写入能力。
- MP-05：调度与执行代次、取消、重启恢复、增量去重和通知；失效平台独立恢复。
- MP-06：多平台选择、每个平台进度、来源筛选、统一商机库；页面不得以一个总绿灯掩盖失败的平台。
- MP-07：逐平台真实运行＋跨平台整链验证。每个首发平台至少完成首次读取、后续增量、无新增、失效恢复和租户隔离验证；目前小红书增量仍待 Windows 实机首轮、续页、重启恢复和旧 worker 回写拒绝验证。来源与读取深度可回查。平台菜单和研究日志不能替代这些验收。

跨行业策略的真实运行、配置效率、商机质量和 14 天试用由 V02-04/V02-05/V02-10 按[产品计划第 7 节](V02_COMMERCIAL_RELEASE_PLAN.md)共同验收；展台历史样本和离线规则测试不替代五类业务的真实客户验证。行业规则和来源均需记录有效/无效样本，不承诺每个行业获得相同数量或效果。

Skill 可以降低新增平台和修改研究策略的成本；持续监控的可靠性仍由执行器、数据事务、会话隔离和逐平台验收支撑。本轮只完成方案及现状核查，未执行真实采集或新增运行时。
