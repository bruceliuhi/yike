## 当前有效入口与已具备部分

从仓库 `desktop/` 目录执行 [build-windows.ps1](../../../desktop/scripts/build-windows.ps1)，完整环境与步骤见 [PACKAGING 的 Windows 部分](../../../desktop/docs/PACKAGING.md#Windows-x64)。Node 要求为 `>=24.15.0 <25` x64；脚本不自动切换 Git 分支或升级代码。

[证据 writer](../../../desktop/scripts/windows-build-evidence.mjs) 为每次运行创建独立 `out/windows-evidence/<runId>/`，记录 Git SHA、dirty、锁文件摘要、运行时版本/架构与摘要、九个阶段及实际产物摘要。包括工作目录中的 ASAR、Setup.exe、RELEASES 和当前版本的 nupkg。失败后未运行阶段保持 `NOT_RUN`，部分完成不能得到 `BUILD_SUCCEEDED`；没有 Node 时 PowerShell 也保留预检失败报告。

[人工模板](../../../desktop/docs/WINDOWS_ACCEPTANCE_TEMPLATE.md) 已覆盖安装、首次启动、任务草稿、三步阻断、正常退出、重启、单实例、卸载和系统 100% / 125% / 150% 缩放。全部默认 `UNTESTED`；即使九个自动阶段通过，JSON 的 `manualAcceptance` 仍为 `UNTESTED`。该性质已有 [writer 回归](../../../desktop/tests/windowsBuildEvidence.test.mjs) 第 145–183 行覆盖，本次只读核验这些断言，没有重报其测试通过数。

回传要求已经明确：同一次运行的 JSON、填写的人工表及脱敏截图；构建失败也回传 JSON，不需要用户凭证、环境文件、客户数据或全部控制台日志。自动阶段成功没有自动升级成人工或真实业务成功。

因此，“Windows 从未构建成功”已经不准确；“当前 9291963 的 R4 Windows 已验收”同样没有证据。旧 4454a45 的 R4 状态和 UI 内容不能自动沿用到新候选。当前目录中的 R4 Mac 测试、截图和包证据也不能替代 Windows 100% / 125% / 150% 或安装生命周期。

用户可以按现脚本开始构建；回传后先核对候选和产物身份，再分别接收自动构建与人工项目。实际平台连接、搜贝计量、外发、真实服务及客户效果仍按原任务书验收，不能靠桌面安装或 TEST 页面转为通过。
