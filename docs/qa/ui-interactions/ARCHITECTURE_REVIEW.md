## 架构判断

1. **可选服务组没有被当作真实能力接入。** `YikeService` 仅增加可选的 `outreach`、`management` 类型入口。生产 `services/client.ts` 未注入这些组，也未新增可调用任意路径或执行命令的 IPC。管理组缺失时统一返回 `MANAGEMENT_UNAVAILABLE`；触达组缺失时返回 `CAPABILITY_UNAVAILABLE`。这允许独立适配器之后实现明确契约，不把按钮、类型或模拟响应变成已有后台功能。
2. **状态与操作职责已拆分。** 领域模块负责响应结构和绑定校验；服务模块声明适配边界；页面负责预览、人工确认和可见状态；管理操作 hook 负责持久请求与回执结算；scope hook 负责用户/空间/revision/设备/服务实例变化；桌面文件写入仅在主进程。服务契约之间采用类型导入，不引入新的运行时互相初始化依赖。P18 复杂写入流程没有继续全部堆入 Settings 页。
3. **P18 预览和执行有明确绑定。** 计划绑定操作、空间、revision、设备、目标版本及备份全文 hash；异步 hash 完成后再次验证作用域才上传，预览响应返回后再核对字段与到期时间。执行同时检查确认勾选、当前 scope identity 和有效期。导出在服务响应、调用原生保存及回执提示前分别检查作用域，旧页面不能在新空间继续保存或显示成功。
4. **外部写入结果未知时保留恢复路径。** 管理操作先持久化 requestId，再执行；网络错误、30 秒超时及错配回执保留锁，只有原请求、类型、空间一致的确定终态可清锁。触达新路径绑定 requestId、机会、用途和版本，发送前重新读取最新持久状态，核对只查原请求。确定失败必须有未投递证明，未知或查无回执不等于可重发。清草稿和退出不删除未决记录。旧两段发送锁没有请求编号时保守保留，不猜编号或自动解锁。
5. **客户端保护与服务端责任没有混淆。** 新服务契约明确服务端必须从认证身份解析租户/空间，验证权限、确认 token、预览及状态版本，并执行持久幂等。客户端 hash、勾选、本机 ledger 或队列记录均不是服务端授权。队列只导航到联系准备，不能将队列文字直接当成已保存发送内容。多设备互斥、真实渠道回执及回复回流尚未由此实现。
6. **备份和更新仍有准确的能力界限。** 前端拒绝异空间、错误产品/版本、超限和可疑凭据字段的备份，但业务数组仍为通用对象；契约要求服务端建立明确字段白名单、关系/归属校验和事务或补偿。更新页面展示服务状态及影响预览，没有在渲染进程添加下载任意安装包、执行安装或回退命令。真实包来源、签名、兼容性和回滚仍是后续适配器必须验证的条件。
7. **隔离视觉数据没有进入生产服务。** 新 TEST 管理与队列数据只由 `tests/visual` 的独立入口创建；生产 renderer 配置及默认服务没有导入。视觉服务拦截实际管理执行、导出、渠道发送，原请求查询返回 UNKNOWN。模拟数据证明 UI 状态可展示，不证明生产授权、备份、投递或更新结果。
